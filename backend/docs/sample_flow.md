# Scheduler Flow — Logic การจัดวันของแต่ละ Step

อ้างอิงจาก `backend/scheduler/engine.js` — สรุปว่าทุกครั้งที่ step หนึ่งจบ engine ตัดสินใจว่า step ถัดไปจะเริ่มวันไหนด้วยลำดับคำถามนี้

## Decision Flow

| ลำดับ | คำถามที่ engine เช็ค | ผลลัพธ์ / กติกา |
|---|---|---|
| 1 | step ก่อนหน้าจบวันไหน? | `prevD` = วันที่ step ก่อนหน้าทำเสร็จ |
| 2 | เครื่องเปลี่ยนไหม? (`m ≠ prevMachine`) | ใช่ + `ENABLE_STICKINESS=1` → บวก 1 วันทันที (กันเวลาขนย้าย/ตั้งคิวเครื่องใหม่)<br>ไม่ใช่ → ไม่บวกวัน เริ่มจากที่เดิมได้เลย |
| 3 | step ก่อนหน้าเป็น day-unit/outsource ไหม? | ใช่ (`isPrevOutsource`) → บวก 1 วันเสมอ ไม่ว่า stickiness จะเปิดหรือปิด (ของบางอย่างต้องรอ "รับของกลับมา" ก่อนถึงจะเริ่มคิวถัดไปได้) |
| 4 | step ปัจจุบันชื่อ/เครื่องตรงกับ `SCHED_DAY_UNIT_KEYWORDS` ไหม? | ตรง → ไปข้อ 5 (day-unit) · ไม่ตรง → ไปข้อ 6 (คิดเป็นนาทีปกติ) |
| 5a | **[DAY-UNIT]** เป็น HEAT-TREATMENT และ `ENABLE_HEAT_DEEP_PLAN=1` ไหม? | ใช่ → ปัดวันเริ่ม/จบเข้า "รอบขนส่ง" (จันทร์/พุธ/ศุกร์ เท่านั้น) แทนการนับ `cycle_time` ตรงๆ |
| 5b | **[DAY-UNIT]** อื่นๆ (DEBURR-MARK-INSPEC, BLACKENING, OQC, ...) | `finish = start + cycle_time` (นับเป็น "จำนวนวัน" ตรงๆ ไม่ผ่านปฏิทิน/capacity เลย) |
| 6 | **[นาทีปกติ]** หา setup ที่ต้องใช้ | jig ของ step นี้ตรงกับ jig ล่าสุดที่เครื่องนี้เพิ่งใช้ (ข้ามคนละ batch ก็นับ) ไหม?<br>ตรง → `setup = MINOR_SETUP_TIME` (40 นาที) · ไม่ตรง/ครั้งแรก → setup เต็มตาม config |
| 7 | **[นาทีปกติ]** ไล่หาวันที่มี capacity พอ | เช็คทีละวันจาก `simStartDate`: เหลือเวลาบนเครื่องนั้น (หลังหักงานของ batch อื่นที่จองไปแล้ว) พอสำหรับ setup+run ไหม<br>พอ → เริ่มวันนั้น · ไม่พอ/ทำได้บางส่วน → ทำเท่าที่พอ ที่เหลือ "ไหล" ไปวันถัดไปที่มี capacity |

> 🟦 สีฟ้า = กติกาที่คิดเป็นนาที/capacity ปกติ 🟨 สีเหลือง = กติกา day-unit (คิดเป็นวัน) 🟩 สีเขียว = จุดตัดสินใจ (decision point)
